## 2. 引き継ぐ相談文の項目

| 相談文の項目名 | 保存元／受信側の項目 |
| --- | --- |
| 相談番号 | `wooddeckConsultationId` → `consult_id` |
| 気になる形 | `wooddeckSelection.plan` の定義済み名称 → `selected_plan` |
| 広さの参考 | `wooddeckSelection.size` の用途・寸法 → `selected_size_example`。確定寸法に置き換えない |
| いま困っていること | `wooddeckSelection.pain` または相談フォーム → `pain` |
| 相談したいこと | `wooddeckSelection.intent` → `intent` |
| 価格診断の商品 | `wooddeckPriceSelection.productName` → `product` |
| 幅・奥行・高さ | `selections` → `width / depth / height`。高さ未定を0mmとして扱わない |
| 税込・商品本体参考価格 | `price` または `priceMin / priceMax` → `reference_price`。施工込み総額ではない |
| 施工希望地域・庭でしたいこと | `qualifiers.city / purpose` または相談フォーム → `city / intended_use` |
| 既存デッキ・設置場所の地面・一緒に相談したいもの | `qualifiers.existing / ground / extras` → 同名の条件項目 |

受信例（テスト用。実相談・実見積もりではない）：

```text
相談番号：WD-20260928-ABC234
ウッドデッキを相談したいです。
気になる形：LPの「敷地に沿う変形デッキ」
広さの参考：2人でお茶を楽しむ（2.7 × 1.8m）
上記は配置の参考です。確定寸法ではありません。
いま困っていること：庭が狭く、置けるか不安
施工希望地域：［市区町村］
```

`［入力］`、空欄、未定は未確認扱い。自由文の自動抽出は推定として保持し、地域・商品・寸法・用途は利用者の確認後に確定する。価格をAIで補完しない。

## 3. LINE担当者への構築指示

1. plusウッドデッキの登録リンク・友だち追加先が正しいことを実端末で確認する。
2. `docs/utage-line-build-spec.md` の挨拶・ラベル・リッチメニューを設定する。作成済み画像は `dist/assets/line/plus-wooddeck-rich-menu.png`。
3. 相談文を受信したら相談番号で既存案件を確認する。新規番号・番号なしの場合も、LINE利用者と進行中案件を照合し二重案件を防ぐ。別利用者の同じ番号を無条件に統合しない。
4. 既に届いた地域・用途・悩み・商品条件を繰り返し質問しない。不足している項目だけ聞く。
5. 写真は最初の問い合わせの必須条件にしない。「室内から庭」「庭から窓」「庭全体」の撮り方を順番に案内する。
6. 問い合わせ受信時刻、地域、用途、写真受領、担当者、調査、見積もり、受注を記録する。自動連携が確認できるまでは有人管理で補い、LP側のクリックを受付件数へ混ぜない。
7. 施工対応店へ渡す前に、共有先・目的・項目を案内して同意を記録する。工事担当は地域の施工対応店、運営者はみちしるべコンサルティング株式会社。

UTAGEでメッセージの構造抽出・外部連携が利用できるかは、契約機能と実際の画面で確認する。本書はそれらが利用可能・設定済みであると保証しない。

## 4. CV定義を統一する

- LINEクリック／コピー成功／友だち追加：中間指標。問い合わせCVではない。
- 問い合わせCV：利用者の初回相談メッセージを受信した時点。挨拶・自動配信は除外。単なる開始メッセージは問い合わせ開始として別集計し、内容のある相談と区別する。
- 有効相談：対応地域・庭の用途または具体的な悩み・検討意思・連絡可能性を確認できた相談。写真は別の進捗指標で、未提出だけを理由に無効としない。
- 提案準備完了：必要な写真／図面・条件がそろった状態。
- 将来の相談API：保存成功を受付の正本にする場合は、LINE受信と同一案件に結び付けてCVを二重計上しない。

`wooddeck_inquiry_message_sent` はLIFFクライアントの送信成功イベントであり、受信側の案件保存を証明するものではない。広告CVの正本へそのまま置き換えない。

相談番号は公開用の照合補助で、認証情報ではない。受信本文だけで広告流入を確定できない。UTMは現在同じブラウザ内に保持するのみで、LINEユーザーや受注へ自動関連付けするサーバー機能はない。

## 5. 完全自動引継ぎの次工程

Instagram内ブラウザ・Safari・LINEは保存領域が別になることがあるため、`sessionStorage` だけでアプリ間の自動引継ぎは完成しない。現在はコピー文を橋渡しにする。

次工程は `docs/conversion-line-ai-proposal-plan.md` に沿って、短期引継ぎトークン・認証付き相談API・写真保存・案件管理を作る。個人情報や写真をURLに詰め込まない。LINE内の専用画面で下書きを確認し、APIの保存成功を受付記録にする。

LIFFの `sendMessages` はLINE内であれば常に使えるわけではなく、起動元と権限に条件がある。現行フォームも利用できない場合はコピーへ戻す。LIFF ID設定前に、正しい公式アカウントのトークからの起動・送信先・権限・受信を実端末で確認する。[LINE公式の送信条件](https://developers.line.biz/en/reference/liff/#send-messages)

Webhookは再配信される場合がある。自社受信APIを追加する際は、署名検証とイベントIDの重複排除を行う。UTAGE連携の場合は受信記録が重複しないことを実験で確認する。[LINE公式のWebhook仕様](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)

## 6. 受入れ確認

| テスト | 合格条件 |
| --- | --- |
| LPで悩み・形・広さを選択 → 商品を選択 → LINE確認 | 具体的な選択名と価格条件を同じ相談文に表示 |
| 価格選択 → LPへ戻る → 条件を見直す | 選んだ商品ページへ戻り、条件を復元。GitHub Pagesのサブパスでも成立 |
| 商品一覧からLINE相談 | 保存済み価格条件を落とさない |
| 高さ未定 | 価格帯と未定表示を維持。本体価格を工事総額と表示しない |
| 未選択／保存が使えない | 空の候補を捏造せず、相談を開始できる |
| コピー成功／失敗 | 状態に合った表示。未送信の段階で受付完了と表示しない |
| 相談フォーム | 入力済み地域・用途・悩みを反映、相談文を確認でき、内容修正もできる |
| iPhone・Android・InstagramからLINE | 追加先、コピー貼付、初回メッセージの実受信を確認。ここは実端末で別途必要 |
| UTAGE受信・再送 | 同じ相談が二重計上されず、入力済み項目を再質問しない |

ローカル検証：`node --test scripts/consultation-state.test.mjs` と `node scripts/preflight.mjs`。自動テストは共有の相談文・URL・保存処理を対象とし、外部LINE／UTAGEの稼働や実端末のアプリ遷移までは証明しない。

### 今回のLP再点検結果

- 390px基準で、サイズ・費用と異なる形の写真入口を先に配置。相談の詳しい写真＋配置図はその後に残し、説明の重複を折り畳みに整理。
- ヘッダーの不自然な改行、320pxでのスワイプ領域の横はみ出し、生成画像を「完成写真」と呼ぶ表現、サイズ図と別寸法の価格例の混同を修正。
- ブラウザで320・390・430pxを確認。LP→商品条件→相談文→LP→選択商品の復元、相談フォームの入力反映・コピー確認・内容修正を検証。テスト用情報のみ使用し、実LINEメッセージの送信は行っていない。
- 共通処理の自動テスト8件が合格。公開時もGitHub Actionsで再実行する。
- 実施工写真、施工込みの正式価格、LINE受信・自動化、実端末でのアプリ遷移の検証は残課題。UI検証を実測CV改善の証拠として扱わない。
